论文阅读笔记

基本信息

标题：

英文：ReAct: Synergizing Reasoning and Acting in Language Models

中文：ReAct：语言模型中推理与行动的协同

作者：Shunyu Yao, Jeffrey Zhao, Dian Yu, Nan Du, Izhak Shafran, Karthik Narasimhan, Yuan Cao

年份：2023

来源：ICLR 2023（普林斯顿大学 + Google Research）

链接：https://arxiv.org/abs/2210.03629

研究背景

大语言模型在语言理解和交互决策上表现很好，但"推理"（如思维链）和"行动"

（如动作规划）一直被当作两件独立的事来研究：思维链能让模型一步步想，但想

出来的结论可能基于错误前提，甚至幻觉；单纯让模型输出动作，又缺少推理过程

支撑，错了也不知道为什么错。论文想解决的问题是：能不能让推理和行动交错

进行，互相补充。

核心思想

输入：任务描述 + 少量上下文示例（few-shot）

↓

方法：交替生成 Thought（推理轨迹）→ Action（工具调用/动作）→ Observation

（环境或工具返回的结果），循环直到任务完成

↓

输出：可解释的完整求解轨迹和最终答案/动作序列

核心点：推理轨迹帮助模型建立、跟踪、更新行动计划并处理异常；行动让模型

能从外部知识库或环境拿到新信息，减少只靠参数记忆带来的幻觉。

系统架构

任务输入

↓

Thought（推理：下一步该做什么、为什么）

↓

Action（调用工具：如 Wikipedia API、环境动作）

↓

Observation（工具/环境返回结果）

↓

循环，直到得到最终答案

技术方法

  • 使用什么模型：GPT-3 和 PaLM 系列，不做微调，靠 1~2 条上下文示例提示
  • 使用什么Agent机制：Thought-Action-Observation 循环（推理与行动交错）
  • 是否使用RAG：没有正式 RAG，但通过 Wikipedia API 检索外部知识，思想

接近"检索增强"

  • 是否使用工具调用：是，工具是 Wikipedia API 和交互环境（ALFWorld、WebShop）

实验设计

机器人平台：无（纯语言任务 + 文本交互环境）

实验环境：HotpotQA（多跳问答）、FEVER（事实核查）、ALFWorld（文本版家务

环境）、WebShop（在线购物环境）

任务：开放域问答、事实验证、交互式决策

评价指标：准确率、成功率、人工可解释性评分

实验结果：相比思维链基线，问答和事实核查的幻觉与错误传播明显减少；在

ALFWorld 上比模仿学习和强化学习方法绝对成功率提升 34%，在 WebShop 上

提升 10%，且只用 1~2 个上下文示例。

与AI-Robot-Demo关系

相同点：项目 Agent 的"任务理解 → 规划 → 工具调用 → 执行反馈"闭环，和

ReAct 的 Thought-Action-Observation 是同一个思想脉络；多轮上下文里保留

前一步结果再决定下一步，本质一致。

不同点：ReAct 让模型自由选择推理和动作，输出没有强约束；项目用 JSON 动作

契约限定动作集合，规划后还要过安全约束层，工业场景不允许模型随便想

干什么就干什么。

可以借鉴：把 Thought 显式化——在计划里保留"为什么选这个动作"的理由，答辩

和论文里可以解释为"可解释规划"的学理依据。

不适合采用：完全放开工具调用权限；工业机器人执行链路上必须保持动作白名单。

个人理解

ReAct 是理解 LLM Agent 的入门必读，它把"想"和"做"揉在一起，解决了纯思维链

容易幻觉、纯行动没有章法的问题。我们的系统其实已经在用这个范式，只是外面

套了一层工业安全壳。读完后更清楚一件事：Agent 的价值不在模型本身，而在

"想一步、做一步、看结果、再想"的循环设计。

论文阅读笔记

基本信息

标题：

英文：Do As I Can, Not As I Say: Grounding Language in Robotic Affordances

中文：做我能做的，而不是说我想说的：把语言扎根在机器人能力里（SayCan）

作者：Michael Ahn 等（Google Robotics / Everyday Robots 联合团队）

年份：2022

来源：CoRL 2022

链接：https://arxiv.org/abs/2204.01691

研究背景

大语言模型装着大量关于世界的常识，但对"这台机器人现在到底能干什么"没有

概念。让它描述"清理洒出来的水"能说出合理的步骤，可这套步骤对一个具体的

机器人、在具体的环境里不一定可行。论文想解决的是：怎么把 LLM 的高层任务

知识，和机器人真实的、当前可行的技能绑在一起。

核心思想

输入：自然语言长任务指令（如"把可乐拿给人类"）

↓

方法：LLM 给每个候选技能打分 p(useful|task)（这个技能对任务有没有用），

技能的价值函数给另一个分 p(feasible|state)（当前状态能不能做），两者相乘

选出"既有用又可行"的下一步技能；机器人执行后返回新的状态，继续循环

↓

输出：可执行的技能序列，机器人真实完成长时程任务

论文题目是点睛之笔：语言模型"说"得头头是道，但机器人只能"做"能力范围内

的事，所以要用能力（affordance）去约束语言。

系统架构

自然语言任务

↓

LLM（PaLM）挑选有用技能 + 价值函数判断可行性

↓

选择 p(useful) × p(feasible) 最高的技能

↓

机器人执行技能，更新状态

↓

循环，直到任务完成

技术方法

  • 使用什么模型：PaLM（语言部分）+ 每个技能的 Q 值函数/价值函数（可行性部分）
  • 使用什么Agent机制：技能选择循环，LLM 只做高层选择，不生成底层控制
  • 是否使用RAG：否
  • 是否使用工具调用：是，所谓"工具"就是一组预训练的低层技能（skills）

实验设计

机器人平台：Everyday Robots 移动操作机器人（真实）；模拟厨房（mock kitchen）

实验环境：仿真厨房 + 真实办公室厨房

任务：101 条长时程自然语言指令，如取放、整理、清洁

评价指标：规划成功率、执行成功率

实验结果：PaLM-SayCan 在 101 条指令上规划成功率 84%、执行成功率 74%；

论文还对比了纯 LLM（不加可行性约束）的效果，证明 grounding 是必要的。

与AI-Robot-Demo关系

相同点：都用"高层理解 + 受限动作"的思路——项目里是 LLM 规划 + 动作契约，

SayCan 是 LLM 选技能 + 价值函数，目标都是让语言模型只在机器人能做到的

范围内出主意。

不同点：SayCan 的可行性约束来自训练过的价值函数，项目用的是规则化的动作

白名单和安全序列规范化，不依赖价值函数训练；SayCan 面向移动操作，项目

面向固定工业机械臂。

可以借鉴：p(useful) × p(feasible) 的"打分选动作"框架，论文里可以用来说明

"为什么 LLM 输出必须受机器人能力约束"。

不适合采用：价值函数训练成本高，工业场景下用规则 + 校验更可控、可审计。

个人理解

这篇是 LLM 机器人的奠基工作之一。"做我能做的，而不是说我想说的"这句话

基本概括了我们的安全约束层存在的理由。区别在于他们用学习出来的价值函数

当"能力边界"，我们用写死的动作契约和安全规则——前者更通用，后者在工业

验收里更讲得清、出了问题好追责。

论文阅读笔记

基本信息

标题：

英文：Inner Monologue: Embodied Reasoning through Planning with Language Models

中文：内心独白：通过语言模型进行具身推理与规划

作者：Wenlong Huang 等（Robotics at Google）

年份：2022

来源：CoRL 2022

链接：https://arxiv.org/abs/2207.05608

研究背景

LLM 在机器人上做规划，通常是一锤子买卖：把任务写进提示词，模型输出一个

计划，机器人照着执行。但真实环境会变——东西没抓稳、目标被挡住了、某一步

失败。如果规划不感知执行结果，后面全错。论文研究：不给模型任何额外训练，

只把执行过程中的自然语言反馈喂回去，模型能不能"边做边改"。

核心思想

输入：高层任务指令 + 环境反馈（成功检测结果、场景描述、人类指令）

↓

方法：LLM 把每一步执行后得到的自然语言反馈写进自己的"内心独白"，据此

更新计划、重排步骤、决定要不要换一种做法；反馈来源可以有多个，全部走

自然语言通道

↓

输出：能应对失败的闭环行为序列

系统架构

任务 + 技能库描述

↓

LLM 规划（生成步骤）

↓

执行步骤

↓

环境反馈（成功/失败/场景/人类提示）转成自然语言

↓

LLM 根据反馈重新规划

↓

循环

技术方法

  • 使用什么模型：LLM（文中主要用 PaLM/LaMDA 类模型做规划），不微调
  • 使用什么Agent机制：闭环规划 + 执行反馈驱动的再规划（inner monologue）
  • 是否使用RAG：否
  • 是否使用工具调用：技能库以文本形式给 LLM 选择，属于受限工具调用

实验设计

机器人平台：仿真桌面机械臂 + 真实桌面机械臂 + 真实移动操作机器人

实验环境：桌面整理任务（仿真和真实）、真实厨房长时程移动操作

任务：整理、取放、按指令摆放等

评价指标：任务成功率（多次运行取平均）

实验结果：闭环语言反馈明显提升高层指令完成率；真实厨房移动操作 120 次

评估的平均成功率约 60.4%，显著高于不带反馈或反馈不全的基线。

与AI-Robot-Demo关系

相同点：项目执行后会把结果回传更新会话上下文，和"执行反馈驱动再规划"

同源；多轮上下文本质上就是简化版的 inner monologue。

不同点：项目目前以"一次规划 + 执行反馈"为主，执行中发现问题默认停止或

由人介入，还没有做到执行时自动重规划；反馈来源也只有工具返回，没有视觉

描述和人类打断。

可以借鉴：把失败反馈结构化后重新喂给规划器，是论文第 6 章"Robot Agent

自主化"展望的直接实现路径。

不适合采用：完全自主的无限重规划在工业上有安全风险，需要加次数上限和

人工确认机制。

个人理解

这篇补上了 Agent 闭环里最容易被忽略的一环：反馈。很多系统演示只拍"规划

成功"，但工业现场 90% 的问题发生在执行层。inner monologue 提醒我，项目

未来的记忆系统不只是存知识，还要存"上次为什么失败"，下次规划时直接用。

论文阅读笔记

基本信息

标题：

英文：Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks

中文：面向知识密集型自然语言任务的检索增强生成（RAG）

作者：Patrick Lewis 等（Facebook AI Research / UCL / NYU）

年份：2020

来源：NeurIPS 2020

链接：https://arxiv.org/abs/2005.11401

研究背景

预训练语言模型把大量事实知识塞进参数里，但有两个硬伤：一是知识密集型任务

上打不过专门设计的检索架构；二是知识"记在参数里"就无法溯源、难以更新——

模型 2020 年学的知识不会自动知道 2024 年的事。论文的思路是：给生成模型

外接一个可检索的非参数化记忆，让答案从检索到的证据里长出来。

核心思想

输入：问题 + 外部文档库（论文里用整个维基百科）

↓

方法：参数化记忆（预训练 seq2seq 模型）+ 非参数化记忆（维基百科密集向量

索引，用预训练神经检索器 DPR 检索 top-k 文档）；检索结果和问题一起送进

生成器，生成时"看着证据说话"

↓

输出：带知识依据的答案/文本

论文给出两种形式：RAG-Sequence（整个输出序列只用同一批检索文档）和

RAG-Token（每个 token 可以用不同文档）。

系统架构

问题

↓

检索器（DPR，对问题编码并与文档索引算相似度）

↓

top-k 文档

↓

生成器（BART 类 seq2seq）用 问题+文档 生成答案

↓

答案

技术方法

  • 使用什么模型：检索器 DPR + 生成器 BART（seq2seq），联合微调
  • 使用什么Agent机制：无
  • 是否使用RAG：这就是 RAG 的开山之作，全文即 RAG
  • 是否使用工具调用：检索器可理解为"外部记忆工具"

实验设计

机器人平台：无（纯 NLP 任务）

实验环境：开放域问答与生成任务

任务：Natural Questions、WebQuestions、TriviaQA（开放域问答）、MS-MARCO

（段落排序）、Jeopardy（生成式问答）

评价指标：精确匹配、F1 等问答指标；生成质量（事实性、多样性）

实验结果：在三个开放域问答任务上达到当时最优，超过参数化 seq2seq 和

任务专用的检索-抽取架构；生成任务上比纯参数化基线更具体、更多样、更

贴近事实。

与AI-Robot-Demo关系

相同点：项目 RAG 模块就是这套"检索 + 生成"思路的工程化：知识库向量化、

查询相似度检索、把 top-k 知识注入规划上下文。

不同点：RAG 论文是"检索器 + 生成器联合微调"的模型方案；项目是"现成嵌入

模型（bge-small-zh-v1.5）+ SQLite 存储 + 混合检索"的轻量方案，不做模型

微调；知识库是自建工业知识，不是维基百科。

可以借鉴：RAG 对"溯源"和"更新"两个问题的论证，正好支持论文第 2 章"工业

机器人为什么需要 RAG"——参数化记忆改不了，外接知识库能随时更新。

不适合采用：联合微调 RAG 模型成本高，对工业知识问答属于杀鸡用牛刀。

个人理解

读这篇最大的收获是理解了 RAG 的本质动机：不是"多一步检索"，而是解决

知识时效性和可溯源问题。我们的实验里"无 RAG 召回 0%、有 RAG 召回 100%"

正好印证了论文的论点——参数里没有的知识，检索能补上。

论文阅读笔记

基本信息

标题：

英文：PaLM-E: An Embodied Multimodal Language Model

中文：PaLM-E：具身多模态语言模型

作者：Danny Driess 等（Robotics at Google / TU Berlin / Google Research）

年份：2023

来源：arXiv 2303.03378（ICML 2023）

链接：https://arxiv.org/abs/2303.03378

研究背景

大语言模型很能"想"，但接不进真实世界——它看不到相机画面，读不到机器人

关节状态。以往做法是语言模型和感知模块分开拼装，接口来回转译，信息容易

丢。论文提出：干脆把视觉、状态等连续传感器信号编码成 token，和文字一起

送进同一个 LLM 训练，让模型直接"看着世界说话、干活"。

核心思想

输入：多模态句子（图像编码 token + 神经 3D 表示 + 机器人状态 + 文本，

交错排列）

↓

方法：把这些模态 token 和文本 token 一起喂给预训练 LLM，端到端训练，

让模型学会跨模态推理；同一套模型同时做机器人规划、视觉问答、字幕生成

↓

输出：机器人动作计划 / 视觉问答答案 / 图像描述

论文强调 positive transfer：在互联网规模的视觉-语言数据上联合训练，能

提升机器人的具身任务表现，模型越大越明显（最大 PaLM-E-562B）。

系统架构

图像 / 3D表示 / 机器人状态 / 文本

↓（编码成 token）

多模态句子

↓

预训练 LLM（端到端微调）

↓

文本输出：计划 / 答案 / 描述

技术方法

  • 使用什么模型：PaLM（LLM）+ 可学习的模态编码器；参数规模 12B~562B
  • 使用什么Agent机制：单模型直接输出规划，没有显式 ReAct 式循环
  • 是否使用RAG：否
  • 是否使用工具调用：部分任务里生成调用技能/API 的计划（如 VIMA 基准）

实验设计

机器人平台：真实移动操作机器人（TÜB 桌面机械臂等）+ 仿真

实验环境：桌面操作、移动操作、VQA 基准（OK-VQA）、具身问答

任务：顺序机器人操作规划、视觉问答、图像字幕、具身推理

评价指标：任务成功率、VQA 准确率、跨任务迁移效果

实验结果：单一模型覆盖多种具身任务；在 OK-VQA 等视觉问答上表现强；联合

训练带来正迁移——视觉-语言数据帮助机器人任务，反之亦然；562B 规模在

具身任务上更强。

与AI-Robot-Demo关系

相同点：都属于"让语言模型参与机器人任务理解"的路线；PaLM-E 的规划输出

也是自然语言计划，和项目的可解释计划同一层级。

不同点：PaLM-E 是端到端多模态大模型，项目是"LLM + 工具 + 后端"的模块化

系统；项目当前没有视觉 token 输入，视觉只作为工具结果文本返回。

可以借鉴：第 6 章"视觉语言机器人"展望的直接参照——把相机画面编码进规划

上下文，代替现在的"视觉工具返回文字描述"。

不适合采用：动辄百亿千亿参数、需要专用算力训练，本科项目不具备条件；

工业现场也更倾向"小模型 + 可审计接口"。

个人理解

PaLM-E 回答了一个方向性问题：感知和规划要不要合并成一个模型。答案在

论文里是"合并更好"，但对我们的系统，现实约束决定了"分开、接口对接"

更可行。读它主要是看趋势——未来如果视觉语言模型 API 便宜到随便调，

我们的视觉层就可以从"识别工具"升级成"感知上下文"。

实验环境：逻辑/几何/数学推理任务、无人机导航（圆形、割草机式巡检）、

操作任务（pick and place 类）、具身 agent 场景

与AI-Robot-Demo关系

相同点：函数库思想与项目动作契约高度一致——都是"先把机器人能力列给模型，

个人理解

做编排，让系统做执行。

零样本/少样本泛化；主要挑战包括数据获取成本、真实世界安全性、泛化到新

环境、评估方法不统一。

与AI-Robot-Demo关系

相同点：项目"LLM 做任务规划 + 语言条件执行"正是综述里"Robot Task

Planning using LLMs"小节描述的方向；项目 RAG 对应综述提到的知识注入。

不同点：项目是工业机器人（ABB IRB120）落地实现，综述覆盖更广的学术

场景；项目用动作契约 + 安全约束解决综述点名的"安全性"挑战。

可以借鉴：综述把"LLM 任务规划"的方法谱系（语言指令/代码生成/上下文学习）

梳理得很清楚，写论文第 1 章研究现状时可按这个谱系组织。

不适合采用：依赖大规模预训练数据的方案，与项目的轻量工程路线不符。

个人理解

这篇确认了一个判断：LLM 在机器人里最成熟、最有说服力的应用就是任务规划，

而不是直接控制。我们的选题刚好站在这个成熟区，同时用安全约束把综述里

点名的"真实世界安全性"问题正面处理了——这本身就是一个可讲的工程贡献。
